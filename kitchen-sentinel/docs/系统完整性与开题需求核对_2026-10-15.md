# 系统完整性与开题需求核对

核对日期：2026-10-15。依据：工作区《开题报告.docx》《要求.txt》、当前源码、MySQL 与网页运行结果、实机记录及本轮用户现场反馈。源码中的“日志对应日期”用于说明实习工作归属；本文件的烧录、测试时间以真实记录为准。

## 当前结论

本地“采集 → 本地保护 → 数据入库 → 实时网页 → 报警留档 → 人工确认／处置 → 命令回执”的链路已运行；蜂鸣器、风扇、继电器和舵机本轮分项动作已得到用户“正常”的现场反馈。系统仍是低压台架原型，尚不能把开题要求中的真实燃气浓度测量、无线远程运行、独立闪光及实体按键全部列为完成。

本轮先补齐已有系统的闭环与维护问题。以下缺口有的需要接线、模块或标定条件，不能只改网页就认定完成。

## 本轮修复和验证

1. 找到同时运行的 8000 新服务与 8001 旧服务。旧服务缺少 escalate 路由，POST 实测返回 405；这是“方法不允许”的直接证据。旧服务已退出，统一使用 8000；新增项目文件锁，重复启动复用已有实例。默认启动改为实物，模拟器从系统测试页单独启动。
2. 转人工继续允许管理员和操作员；只读角色写入返回 403，写请求仍校验 CSRF。数据库事务改为响应前提交，避免登录成功后立即请求偶发 401。
3. 数据提交后唤醒实时连接，并以一秒心跳更新状态；浏览器检测停滞、重连、两秒查询兜底及前后台切换补查。已经触发的本地危险直接入报警，不再重复等待平台持续时间。
4. 正式页面仅使用硬件来源，模拟场景、测试报警、模拟控制及硬件诊断集中到“系统测试”。保留旧测试记录，并按来源隔离统计。
5. 新版固件支持七项控制能力，危险始终优先。蜂鸣器、风扇、继电器测试限时三秒；舵机测试仅下发关阀，不测试开阀；火灾拒绝消音和执行器测试。
6. 平台三项阈值通过版本化信箱同步到 MCU，并上报实际应用值。持续时间、恢复时间、回差及人工升级时限仍由平台状态机管理，本地保护可先于平台立即动作。
7. 控制命令失败及超时单独形成控制执行异常；同类重试成功只标恢复，原记录继续待人工确认与核查。
8. Keil 全部编译源文件与头文件依赖检查均在工程内；完整编译 0 Error / 0 Warning，生成 28 份代码浏览文件。

实机证据：版本 4，72 MHz，33,560 字节下载读回零差异；ADC 错误与算法自测失败为 0。五项命令得到 MCU 成功回执；蜂鸣器、风扇、继电器观察到 on → off，舵机保持 closed。用户本轮回复“正常”，作为独立的现场反馈保存，不能等同于增加了阀位传感器。

## 补齐顺序与维护事项

优先补齐真实燃气检测和标定、MB026 无线链路、独立闪光与实体按键。实物阀门、阀位／电流反馈及掉电后保持关阀必须一起设计；在此基础上再加入看门狗恢复，避免单纯复位导致阀门状态被清空。普通模型风扇只用于无可燃气体的低压台架，不能把此策略直接移用于真实燃气现场。

维护应补充数据库备份与恢复实测、遥测保存时长与归档策略、长期稳定运行及拔线重连记录、模块断线／卡死测试、账户停用与操作复核。将模型接入、外部推送和远程部署作为后续独立验收项；仍存在基础缺口时，先完成这些验收，再增加新的展示功能。

本机运行入口：项目 start.py，默认实物模式；当前访问 http://127.0.0.1:8000/。系统测试内启停的模拟器由后端归属管理，服务退出时回收。旧版 8001 地址不再作为入口。
